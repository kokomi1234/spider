缺陷 A ｜ 下拉菜单弹出内容超出页面可视区导致不可见

判定：复现
两个独立场景均复现，且最坏情况下面板几乎 100% 不可见。
场景面板高度被容器裁掉超出视口底部可见比例是否具备上翻能力
A1 订阅弹窗滚动容器 .sub-body 内的下拉 288px 276px 159px 4%
(12px)		 无 is-dropup，面板未挂载到 body
A2 页面底部固定定位的下拉 288px — 282px 2% 无 is-dropup，面板未挂载到 body
A3 三个页面筛选区默认位置的下拉（对照） 70–216px 0 0 100% 无需上翻（下方空间充足）

根因定位

承载样式
theme.css:329 .searchable-select{position:relative} + theme.css:383-397 .searchable-select-dropdown{position:absolute; top:calc(100% + 4px); max-height:288px} —— 位置完全由 CSS 写死，永不上翻。
逻辑层
js/ui/searchable-select.js（609 行）通篇没有任何定位/避让逻辑：不读取 window.innerHeight、不计算 spaceBelow/spaceAbove、不判断滚动父容器、不提供 is-dropup 类、不把面板挂到 document.body。
同类控件
multi-select 存在完全相同的缺陷，且约束更弱：theme.css:1542 .msel{position:relative} + theme.css:1581-1593 .msel-panel{position:absolute;top:calc(100% + 4px)}，连自身 max-height 都没有（仅内层 .msel-list 限 240px）。
对照实现
js/ui/date-picker.js:7-13 与 :363-472 已完整实现正确方案：enterFloat() 把面板 document.body.appendChild(panel)、根据 spaceBelow/spaceAbove 决定 openUp、空间不足时压 maxHeight、并用 scrollToRevealPanel() 自动滚动容器腾出空间。
关键结论：这不是"某个页面写漏了"，而是同一套自研控件体系里能力不对称。 同一个弹窗里，日期字段点开能自动上翻/压高，紧挨着的下拉字段却完全不可见 —— 用户会认为页面坏了。

针对性改进建议

  1. 抽取统一浮层定位能力（首选，一次解决两个组件）。把 date-picker.js 的定位逻辑提炼为公用模块（如 js/ui/popup-position.js，导出 position(anchorEl, panelEl)），在"下方空间 < 面板高度且上方空间更大"时加 is-dropup 并把 top 换成 bottom:calc(100% + 4px)；面板挂到 document.body 以脱离任何 overflow 祖先；空间不足时压 maxHeight = 可用空间 - 间距（保留 overflow-y:auto）。
  2. 在 searchable-select.js 中接线。在 openDropdown()（:316-331）调用定位函数；在 onWindowResize/容器 scroll 时重定位；closeDropdown()（:333-342）恢复原状。注意与既有 document.mousedown 捕获监听（:520-523）配合：面板脱离 container 后，container.contains(e.target) 判断会失效，需一并改为"面板内也不关闭"。
  3. multi-select 同步接入（js/ui/multi-select.js:43 的 .msel-panel），并把 .msel-panel 补上 max-height。
  4. 补一条回归测试。在 tests/smoke-browser.js 里增加断言：把组件分别置于"距视口底 8px"和"滚动容器底部"两种位置，打开后断言 panel.getBoundingClientRect().bottom <= 可视底边 且可见比例 ≥ 90%。现有冒烟脚本只断言了 floating/visible:true（对应日期控件），未覆盖下拉。

8.1 评估方法

  • 多智能体协作：派出 3 个并行专项评估智能体，分别负责可用性、易用性、一致性维度，各自独立通读页面与组件源码并产出问题清单（含 文件:行号）。
  • 主评估者独立复核：所有智能体给出的关键结论均被逐条复核。复核中纠正了 2 处不实结论——例如某智能体声称 task.html:839 存在 #loadingMask，经 Grep 验证该文件不存在任何 loading 相关元素，故本报告按"task 页缺少加载能力"记录；某智能体称 !important 共 18 处/8 文件，实际项目自身文件仅 4 处（其余为 vendor/ 第三方代码），已按实测值更正。
  • 无头浏览器实测：用项目自带的 vendor/playwright-core + 本机 Chrome，以静态服务器加载真实页面，读取 getBoundingClientRect()、getComputedStyle() 与元素级裁剪祖先，量化"可见像素比例""表头相对容器偏移"等指标，而非仅凭代码推断。
  • 量化统计：对术语、令牌使用、空态文案、无障碍属性、!important、window._ 等做全仓 Grep 计数（排除 vendor/ 与 cache/ 录包）。
