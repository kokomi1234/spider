- **前端表现**：实测 `.overlay.show.dlg-util-overlay` 里 `h2` = 「请确认」、`.dlg-util-body p` = `""`、

  更稳的做法：`confirmBox` 里对 `{text|message|body}` 三种叫法都认，或直接要求必填并加一条单测

## 二、逻辑错误（状态不一致 / 结果不对）

### D-2 ｜命名截断把真实名字吃掉：你的库里现在有一条显示成单个字母「B」

- **影响等级**：逻辑错误（用户报过两次，同一函数的未修分支；本轮双重证实）
- **复现操作**：`/publish` → 「⭐ 保存到首页」→ 回 `/home` → 「重命名」输入 `发布查询-2` → 确 认
- **前端表现**：卡片标题节点 `.saved-name span:last-child` = `"2"`（记录里 `name` 仍是 `"发布查询-2"`），
  整行读作「服务发布数据查询2」；截图 `/tmp/ops-renamed-title.png`、`/tmp/s1-shortcode.png`。
  用你**真实团队库**（只读）里 11 条记录直喂原函数，实跑：
  | 库里存的 `auto_name` | 首页「我的」/部门榜实际显示 |
  |---|---|
  | `调用方系统：E00404-网上银行服务前端-海外个人网银-B` | **`B`**（库里有 2 条这样） |
  | `E00301-互联网金融服务平台-BOCNET-G-IFS` | `BOCNET-G-IFS` ✅ |
  | `调用方系统：BOCNETC-O-MAPSN` | `BOCNETC-O-MAPSN` ✅（`9f542f1` 修的就是它） |
  | `调用方系统：E00406-网上银行服务前端-海外个人手机银行` | 原样不截（没有英文尾巴） |
  同类可复现形态：`服务-发布-check1`→`1`、`BOCNET G IFS`→`IFS`、
  多值串 `调用方系统：BOCNETC-O-MAPSN · 批次：261`→**`BOCNETC-O-261`（拼出假编码）**、
  三个 label 拼串 `E00301/E00406/2611`→**`2611`（名字塌成一个数字）**。

  改成对每个 `-` 段取尾部 `[A-Z0-9]+`，于是**任何单个大写字母或纯数字都被当成编码**，
  从末尾收集到空段即停 → `海外个人网银-B` 只剩 `B`。另有两处放大：
  `:407` 走 summary 分支时**先硬截 30 字再截码**（可能正截在编码中间）；
  `js/page/home.js:125` 的 `shortOf(condTitle || item.name)` 对**用户自己起的名字**也做截断。
- **修复建议**：① `shortCode` 只在尾部整体匹配到「像编码」的形态时才动（要求段长 ≥2、含字母、
  遇 `·`/`：`/中文即停），取不到就原样返回；② 用户手填的 `name` **不进 `shortCode`**（只截条件生成的默认名）；
  ③ `condNameOf` 改成"先截码、再限长"。改完补 `tests/saved-query.test.js` 用例覆盖上述 6 种形态。

### D-3 ｜没设当前用户时角标谎报「已同步」（违反 2026-09-21 拍板）

- **影响等级**：逻辑错误
- **复现操作**：全新浏览器 context（localStorage 全空）打开 `/home`，**不登录**
- **前端表现**：实测 t+700ms ~ 4900ms 全程 `state='shared'`、角标显示「已同步」；
  未登录再存 1 条仍是「已同步」。
- **根因**：`js/ui/saved-query.js:1306`（`pushToServer` 的**无用户分支**）记的是
  `recordSync({ ok: true, total: …, …meta })`，**漏了 `noUser: true`**，而 `recordSync`（`:1133`）
  见 `file` 有值就判 `shared`；`js/page/home.js:890` 每次加载都主动 `pushToServer`，
  把 `syncFromServer`（`:1244`，它**正确**带了 `noUser: true`）记下的 `nouser` 覆盖掉。
  即：09-21 那次修的「没设用户不许说已同步」只覆盖了 GET 那条路，POST 这条路漏了。
- **修复建议**：无用户分支同样传 `noUser: true`（判据取 `CurrentUser.get()`，与 `:1244` 同口径），
  并在 `tests/saved-query.test.js` 补一条「未登录 push 之后角标仍是 nouser」的防线用例。

### D-4 ｜把同事导出的文件导给另一个登录人是**静默空操作**，提示却报「合并 2 条」

- **影响等级**：逻辑错误（本项目的标准部署形态下必然命中：全组共用一份代理、一个团队库）
- **复现操作**：X 登录 → 首页「导 出」→ 另一个身份 Y 登录 → 真点「导 入」选 X 的那个文件
- **前端表现**：导入前后 Y 的「我的」都是 1 张卡；toast 报「新增 0、**合并 2**、库内 1」，让人以为导成了。
- **代理层/网络表现**：服务端全集仍 3 条不变、X 那两条 `saverKeys` 仍是 `["4711510"]`、
  `?user=<Y>` 仍 1 条 → **Y 一条也没得到**。
- **根因**：`importJson`（`saved-query.js:1026`）按 09-21 拍板把 owner 改成 Y，但
  `sameQuery`（`:347`）**先按 id 短路返回 true**，`page`/`userKeyOf(owner)` 的比较在 `:349-350`，
  永远走不到；`mergeItems`（`:972` 起）只在 `!same.owner` 时才补 owner，于是命中的是服务端**X 那一行**、
  归属不变。函数头上的注释「正确的判据是同一份筛选条件 + 同一个人」与实现自相矛盾。
  `88e0e26` 的「导入归当前用户」只在**另一套库**才生效。
- **修复建议**：导入路径**关掉 id 短路**（只按 `fingerprint` + 同人判同），或给 incoming 换发新 id；
  并把 `added === 0 && merged > 0` 的提示从「已导入」改成「你已经有这些了」。

### D-5 ｜记录被静默丢弃、代理已如实回传的计数前端不读

- **影响等级**：逻辑错误
- **复现操作**：`POST /local/saved-queries` 提交 3 条（分别缺 `page` / 缺 `id` / 缺归属人）
- **代理层/网络表现**：`200 msg="已合并保存" truncated=0`，服务端全集条数 **4003 → 4003（0 条入库）**。
  另一测：提交 2100 条 → `200 truncated=100 msg="已合并保存（超出 2000 条上限，丢弃 100 条）"`，
  代理侧计数**是对的**（上轮 P2 已修）。
- **前端表现**：角标照说「已同步」。
- **根因**：`lib/queries-db.js:304`（`!it.id || !it.page` 直接 `return`）与 `:312`（`!uk` 直接 `return`，
  `1b89721` 引入的孤儿行防线）两处都**不计数**；前端 `js/ui/saved-query.js:1296` 只取
  `file/storage/people`，**从不读 `truncated`、也不看 `msg`**。
- **建议**：`upsert` 回执加 `stored/skipped`，前端据此提示；注意 `:312` 这条路正盖住
  「未登录保存 → 登录后认领」，改的时候要连带 E 的 M2 场景回归。

### D-6 ｜前端超时与代理超时同为 20000ms —— 「超时后降级读本地缓存」永远来不及

- **影响等级**：逻辑错误（上轮报告未覆盖的盲区，本轮补测出来）
- **复现操作**：后端替身永不响应；`/tmp/cacheD/<key>.json` 预置一条录制；前端点查询
- **代理层/网络表现**：代理在 **20006ms** 交付缓存回放（`X-Served-From: cache`，机制本身是好的）；
  对照 `/health?t=1` 走同一转发路径也是 20006ms。
- **前端表现**：`api-client` 在 **20000ms** 就 abort，用户看到
  「⚠️ 查询失败：请求超时（20000ms 未响应）」—— 而缓存里那份数据本可以显示出来。
- **根因**：`js/core/api-client.js:37` `DEFAULT_TIMEOUT = 20000`（注释写着「与代理层 PROXY_TIMEOUT 对齐」）
  与 `proxy.js:99` `TIMEOUT = … || 20000` —— 注释说的"对齐"实际是**撞车**。
- **建议**：前端 > 代理（例如 22s / 20s），并把两个值收成同一处常量或配置项，别让它们各写一遍。

### D-7 ｜`PROXY_TIMEOUT` 只在冷启动有效，但横幅与 `/reload` 都说已生效

- **影响等级**：逻辑错误（改了不生效 + 谎报）
- **复现操作**：`.env` 写 `PROXY_TIMEOUT=700` 冷启动 → 生效（705ms 掐断）；改成 `9000`，
  等 1.9s（轮询周期内）或直接调 `/reload` → **仍 705ms**
- **代理层/网络表现**：`/reload` → `200 {"code":200,"msg":"reloaded","keys":["PROXY_TIMEOUT"]}`；
  `/health` 里**没有 timeout 字段**，用户无从核对。启动横幅原话：「热更新 .env：修改后自动生效（约 1.5 秒）」。
- **根因**：`proxy.js:99` 是启动时求值的 `const`，`refreshConfig()` 不管它（全文件仅
  63/99/546/589/1374 五处引用，无一在刷新路径里）。
- **建议**：`refreshConfig` 里同步 `TIMEOUT`；或把横幅/`/health` 改成如实播报（`/health` 加 `timeout` 字段）。

### D-8 ｜`/health` 带查询串就掉进转发层；未知 `/local|/admin|/cache` 路径同样落到内网

- **影响等级**：逻辑错误（**推翻上轮代理报告 §2.7「`/local/*` 未知路径不落到转发 ✅ 404」**）
- **复现操作**：`GET /health?t=1`；`GET /local/unknown-x`、`/admin/unknown-x`、`/cache/unknown-x`
- **代理层/网络表现**：`/health?t=1` → **502 @20006ms**、`target` 指向内网（`/health` 无查询串时 200 @2ms）；
  三种未知本地路径**全部被原样转发**（实测回显 `target="http://127.0.0.1:3097/local/unknown-x"`）；
  而 `/reload?x=1`、`/cache/list?_=1` 反而正常（它们用了去查询串的判据）。
- **根因**：`proxy.js:837` 用 `req.url === '/health'` 精确匹配，而其余本地端点用 `cachePath`
  （`proxy.js:854`，`new URL(...).pathname`）—— 两套判据不一致。
- **建议**：统一走 `cachePath`；`/local|/admin|/cache` 前缀未匹配上具体端点时**直接 404，不进转发层**。

### D-9 ｜服务端删除后，已打开的标签页无限期停留旧列表（无轮询、无推送）

- **影响等级**：逻辑错误（团队共用一套库时的常态：同事删了你还挂着）
- **复现操作**：A/B 两标签同为工号 88001 → `curl POST {items:[], deletedIds:["sq-gone"]}` → 看 B
- **前端表现**：B 在 **3s、10s** 后仍显示「会被删的查询」、角标仍「已同步」；
  刷新后与服务端一致（2 条）。反向：A 不刷新却出现了 B 新存的那条（跨标签 `storage` 事件，**只有登录段有**）。
- **代理层/网络表现**：`grep setInterval|EventSource|WebSocket` 在 `js/` 与 `proxy.js` **0 命中** ——
  确实没有任何推送/轮询通道，一致性只靠「加载时 `syncFromServer` + 本机操作后 `pushToServer` + 跨标签 storage 事件」，

- **建议**：要么加 30~60s 低频重取，要么把角标文案改成「上次同步 N 秒前」（后者不动架构）。
  注：`memory.md` §1 不允许写说明性提示文字，改角标内容属于「空态一行/反馈」范围内，可谈。

### D-10 ｜`UserToken` 只登记了一处，掉脚本零报警、静默回落管理员 token

- **影响等级**：逻辑错误（违反 `AGENTS.md` §6.2「改脚本要三处同步登记」）

- **前端表现**：`typeof window.UserToken === 'undefined'`；控制台**没有任何**
  `[bootstrap] 缺少运行时依赖`（只有两条无语义 404）；🔑 按钮变「🔑 管理员 token」；
  查询照发（200、10 行）但请求头**无 `x-user-token`** → **静默用管理员 token，订阅等写操作无声禁用**。
- **根因**：四个 HTML 都引了脚本（`index.html:413`、`publish.html:987`、`task.html:463`、

## 三、体验缺陷

### D-12 ｜真双击「查 询」= 点了没反应（一次操作被吞）

- **影响等级**：体验缺陷（日常高频：手快的人会连续碰到）
- **复现操作**：`/publish` 填提供方系统后**双击**「查 询」（`dblclick`，delay 40ms）
- **前端表现**：`.overlay.show` 数 = **0**、`getPublishDataList` 请求数 = **0**、无 toast、表格仍是初始 1 行。
  对照单击 → 正常弹 1 个确认框。
- **根因**：确认框在第一次 click 的 handler 里同步打开，第二次 click 落在遮罩上，而
  `js/ui/dialog-utils.js:293` 的遮罩点击是 `done(null)` —— **点遮罩等于「取消」**。
  于是双击 = 「打开 → 立刻取消」。
- **建议**：弹开后 300ms 内忽略遮罩点击，或给「必须表态」的确认框关掉遮罩取消（这类框点外面不该等于选「取消」）。

### D-13 ｜连点两次查询会叠两层确认框，第二层压在结果上

- **影响等级**：体验缺陷
- **复现操作**：`btn.click(); btn.click()`（间隔短于用户反应时间）
- **前端表现**：`.overlay.show` = **2**（两个同名「数据量可能过大」）；点上层「继续查询」→
  请求 1 次、结果 10 行，但 overlays 仍 = **1**，再点会继续查一次。
