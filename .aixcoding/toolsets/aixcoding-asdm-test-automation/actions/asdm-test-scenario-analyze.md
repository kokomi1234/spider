## Purpose

本指令引导 AI 模型分析 User Story 卡片中以 Given-When-Then 格式描述的验收标准（AC），识别需要实例化的变量与测试维度，基于业务语义生成初始数据需求清单，产出结构化的示例分析文档，为后续的 `asdm-test-spec-ui-generate`（示例生成）阶段提供输入。

**重要**：本阶段不依赖源码仓库。此时源码可能尚未实现，分析基于 AC 文本和业务语义进行。源码中的实际字段约束（如长度限制、枚举值、校验规则）后续可由开发人员补充和校正。

本阶段对应 Specification by Example（SBE）流程中的 **分析（Analyze）** 阶段，是"分析 → 实例化 → 校验"三阶段流程的第一步。

## Language Setting

默认使用**中文（简体中文）**作为输出语言。所有生成的内容均使用中文，并遵循中文写作规范。

如需切换语言，可在工作区根目录创建 `.aixcoding/config.json` 配置：
```json
{
  "language": "zh"
}
```
支持的语言：`zh`（中文，默认）、`en`（英文）。

## Context Injection

在开始分析之前，AI 模型必须读取 User Story 卡片，理解验收标准的业务语义。

### Context Files to Read (Required)

1. **User Story 卡片** (Required - 必须读取)
   - Path: `.aixcoding/workspace/stories/<feature-id>/<us-id>.md`
   - Purpose: 获取 User Story 的用户故事、验收标准（AC）以及（如存在）技术依据小节，作为实例化分析的输入
   - **如果该文件不存在**：提示用户检查 User Story ID 是否正确，或该 User Story 卡片尚未生成

### Progressive Context Loading Strategy

1. **初始阶段**：读取 User Story 卡片，提取用户故事、AC，以及技术依据小节（如存在）
2. **深入阶段**：逐条分析 AC 的 Given/When/Then，识别变量和测试维度
3. **补充阶段**：如需理解业务背景，读取 Feature 准备文档

**IMPORTANT**: 本阶段不扫描源码仓库。但 User Story 卡片中可能已内嵌来自 PRD 的「技术依据」小节（条件性生成），其中的数据模型字段、接口参数等可作为已知约束直接使用，减少"待源码验证"项。

## Steps to 示例分析

### 1. 加载 User Story 卡片

1. 接收用户指定的 User Story ID（如 `FT-001-US-01`）
2. 从 User Story ID 解析 Feature ID（如 `FT-001`）和 User Story 序号（如 `US-02`）；如需定位卡片文件，读取 `.aixcoding/workspace/stories/<feature-id>/<us-id>.md`
3. 读取 `.aixcoding/workspace/stories/<feature-id>/<us-id>.md`
4. 提取关键信息：
   - 用户故事（作为一个…我想要…以便…）
   - 验收标准列表（AC-1, AC-2, ...），每条包含 Given/When/Then
   - 依赖关系
   - 备注（可能包含技术约束、设计要点）
   - **技术依据小节（如存在）**：包含关联 PRD 章节（含锚点与摘录版本号）、涉及数据模型、涉及接口、复杂度提示

**如果 User Story ID 未指定**：
- 扫描 `.aixcoding/workspace/stories/` 目录
- 列出所有已有 Feature 下的 User Story（ID + 名称 + 状态）
- 提示用户选择要分析的 User Story

**如果 User Story 卡片不存在**：
- 提示用户该 User Story 卡片尚未生成，需先完成 User Story 拆分

#### 1.1 读取并校验技术依据小节（如存在）

若卡片含「技术依据（估算参考，非实现规范）」小节：

1. 提取其中的**涉及数据模型**（字段/枚举/表）和**涉及接口**（endpoint/参数），作为变量已知约束的补充来源
2. **PRD 版本漂移检测**：比对卡片记录的摘录 PRD 版本号与当前 PRD 文档（`FT-{id}-{name}-PRD.md`）的实际版本；若当前版本更高，提示"技术依据可能已过期，建议核对 PRD 原文"，并将其中的约束降级为"待源码验证"
3. **与 AC 严格分离**：技术依据仅用于填充变量识别表的"已知约束"列，不得混入 AC 的 Given-When-Then 分析（AC 保持业务语言）

### 2. 识别待实例化的变量

逐条分析 AC，识别其中需要实例化的变量、参数和条件：

#### 2.1 识别变量类型

| 变量类型 | 说明 | AC 中的特征词 | 示例 |
|----------|------|---------------|------|
| 用户角色 | 操作主体的角色 | "用户是…角色的成员" | Owner / Admin / Member |
| 身份验证方式 | 用户登录/身份核验所需的具体字段 | "已登录"、"已验证"、"通过身份验证" | 姓名+生日 / 手机号+验证码 / 用户名+密码 |
| 输入数据 | 用户输入的字段值 | "用户输入…"、"提交…" | 用户名、密码、空间名称 |
| 系统状态 | 前置数据/环境状态 | "已存在…"、"系统中有…" | 已创建的团队空间 |
| 操作参数 | 操作的具体方式 | "点击…"、"选择…" | 点击进入、选择某个空间 |
| 预期结果 | 验证的输出 | "展示…"、"返回…" | 展示管理视图、返回 200 |

> **特别说明**："身份验证方式"必须落到具体字段（如"用户名+密码"），不能停留在"已登录"这种抽象表述。这是因为下游 `asdm-test-spec-ui-generate` 会直接把这个变量写入 Background，模糊的表述会导致生成的 Scenario 无法真正驱动 UI 自动化。若 AC 和技术依据小节均未给出具体验证字段，必须在数据需求清单中标注为"待源码验证"，不得由生成阶段自行编造。

#### 2.2 标注变量的约束来源

由于本阶段不扫描源码，每个变量的约束来源需标注：

| 约束来源标记 | 含义 | 说明 |
|--------------|------|------|
| `AC 语义` | 从 AC 文本推断 | 如 AC 提到"Owner/Admin/Member"，则角色枚举来自 AC |
| `业务常识` | 基于业务领域知识推断 | 如用户名通常非空、有长度限制 |
| `PRD 技术依据` | 来自卡片「技术依据」小节（条件性） | 如 PRD 已给出字段枚举、endpoint 参数；需与 AC 严格分离，仅填入"已知约束"列 |
| `待源码验证` | 需后续从源码补充 | 如字段精确长度、格式校验规则、边界数值；当无技术依据或技术依据已过期时使用 |

**优先级**：`AC 语义` > `PRD 技术依据` > `业务常识` > `待源码验证`。当技术依据小节存在且 PRD 版本未漂移时，应优先采用其约束，减少"待源码验证"项。

### 3. 定义测试维度

为每条 AC 定义测试维度，明确需要覆盖的测试场景类型：

#### 3.1 三类测试数据

| 数据类型 | 说明 | 设计目标 | 示例 |
|----------|------|----------|------|
| **正常值（Happy Path）** | 符合业务预期的合法输入 | 验证功能正常工作 | 角色为 Owner 的用户进入管理视图 |
| **边界值（Boundary）** | 处于约束边界的输入 | 验证边界处理正确性 | 字符串恰好达到最大长度（具体数值待源码验证） |
| **异常值（Error Path）** | 违反业务规则的非法输入 | 验证错误处理和校验 | 必填字段为空、角色越界、格式不匹配 |

#### 3.2 为每条 AC 分配测试维度

针对每条 AC，列出需要覆盖的测试维度组合：

**示例**：
```
AC-1: 管理视图页面展示
- 正常值: Owner 角色、Admin 角色、Member 角色（三种合法角色各一例）
- 边界值: Member（最后一个枚举值）→ 待源码验证是否有其他枚举
- 异常值: 未加入任何团队空间的用户尝试访问、非法角色

AC-2: 基本信息展示
- 正常值: 空间名称、描述、创建者信息均存在
- 边界值: 描述为空字符串（如允许）→ 待源码验证描述是否可选
- 异常值: 无（展示类 AC，异常场景较少）
```

### 4. 生成数据需求清单

汇总所有 AC 的变量和测试维度，生成数据需求清单。对于无法从 AC 语义确定的约束，标注为"待源码验证"：

| 变量名 | 来源 AC | 约束来源 | 正常值示例 | 边界值示例 | 异常值示例 |
|--------|---------|----------|-----------|-----------|-----------|
| 身份验证方式 | Background/前置条件 | AC 语义 / PRD 技术依据 / 待源码验证 | 姓名 "张三" + 生日 "1990-05-12" | 不适用（非枚举型） | 姓名与生日不匹配 |
| 用户角色 | AC-1, AC-3, AC-4 | AC 语义 | Owner | Member（末位枚举） | Guest（非法角色） |
| 空间名称 | AC-2 | 待源码验证 | "研发团队空间" | 待源码验证（最大长度） | 超长字符串（具体长度待源码验证） |
| 空间描述 | AC-2 | 待源码验证 | "用于研发协作" | 空字符串（如允许） | 待源码验证 |
| 空间类型 | AC-2 | PRD 技术依据 | "私有" | "公开"（末位枚举，来自技术依据） | "归档"（非法取值） |

## Execution Guidelines

### When to Use This Action

使用本 action 的场景：
- User Story 卡片已生成（位于 `.aixcoding/workspace/stories/<feature-id>/<us-id>.md`）
- 需要将抽象的验收标准（AC）实例化为具体测试数据前的分析阶段
- 开发团队编写 BDD/Cucumber 自动化验收测试前的需求实例化准备
- **源码尚未实现**，需要先基于 AC 语义和业务常识进行分析

### 变量识别原则

1. **逐条分析 AC**：每条 AC 的 Given/When/Then 都可能包含待实例化变量
2. **区分变量类型**：用户角色、输入数据、系统状态、操作参数、预期结果
3. **标注约束来源**：每个变量标注约束来源（AC 语义 / 业务常识 / 待源码验证）
4. **标记待源码验证项**：无法从 AC 确定的约束（如精确长度、格式规则）标记为"待源码验证"

### 错误处理

- **User Story 卡片不存在**：提示用户该 User Story 卡片尚未生成，需先完成 User Story 拆分
- **AC 过于抽象无法识别变量**：提示用户该 AC 可能需要进一步细化
- **User Story 状态为"草稿"**：提示用户该卡片可能尚未定稿，但允许继续

## Usage

To use this instruction, the AI model should:
1. 检测响应语言
2. 接收用户指定的 User Story ID
3. 读取 User Story 卡片，提取用户故事和验收标准
4. 逐条分析 AC，识别待实例化的变量并标注约束来源
5. 为每条 AC 定义正常值、边界值、异常值三类测试维度
6. 生成数据需求清单，标记待源码验证项
7. 生成示例分析文档并保存
8. 呈现分析摘要并提示下一步

## Output Summary

完成分析阶段后，将生成以下产出：
- 示例分析文档：`.aixcoding/workspace/specs/<feature-id>/<story-id>/<story-id>.example-analysis.md`

所有文件保存在 `.aixcoding/workspace/specs/<feature-id>/<story-id>/` 目录下。
