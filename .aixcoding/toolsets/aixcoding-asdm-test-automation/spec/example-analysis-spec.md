# 示例分析文档规范

## Language Guidelines

本规范定义的文档必须使用环境检测到的响应语言。确保文档中所有内容遵循：

1. **语言一致性**: 整份文档使用同一种语言
2. **写作规范**: 遵循所使用语言的写作风格和格式要求
3. **表达清晰**: 确保内容在所选语言下清晰易懂

**支持的语言**:
- 中文（zh，默认）
- 英文（en）
- 其他基于环境检测的语言

---

## Overview

本规范定义了示例分析文档（`example-analysis.md`）的结构和格式要求。此类文档用于记录 `asdm-test-scenario-analyze` action 的分析结果，包括 User Story 验收标准摘要、待实例化变量识别（标注约束来源）、测试维度定义和数据需求清单（标注待源码验证项）。

**重要**：本阶段不依赖源码仓库。变量的约束来源标注为"AC 语义"、"业务常识"、"PRD 技术依据"（如卡片含技术依据小节）或"待源码验证"。源码中的实际字段约束后续可由开发人员补充和校正。

**主要用途**:
- 作为 `asdm-test-scenario-analyze` action 的输出文档
- 为后续 `asdm-test-spec-ui-generate` 生成 Gherkin `.feature` 文件提供分析依据
- 提供应源码验证项清单，便于后续校正

## Section Guidelines

### 1. User Story 概述

**要求**：
- 用户故事从 User Story 卡片原样复制，不做修改
- AC 摘要表需精简 Given/When/Then 为简短描述
- AC 编号与 User Story 卡片保持一致

### 2. 待实例化变量识别

**要求**：
- 逐条分析 AC 的 Given/When/Then，提取所有待实例化变量
- 变量类型取值：用户角色、输入数据、系统状态、操作参数、预期结果
- **约束来源**必须标注，取值：
  - `AC 语义`：从 AC 文本直接推断的约束（如 AC 提到"Owner/Admin/Member"）
  - `业务常识`：基于业务领域知识推断的约束（如用户名通常非空）
  - `PRD 技术依据`：来自 User Story 卡片「技术依据」小节（条件性生成）的约束（如 PRD 已给出的字段枚举、endpoint 参数）
  - `待源码验证`：完全依赖源码才能确定的约束（如精确长度、格式规则）
- 已知约束列填写从 AC 或业务常识确定的约束，无则填"无"
- 待源码验证项列填写需后续从源码补充的约束

### 3. 测试维度定义

**要求**：
- 每条 AC 单独一个子章节
- 三类测试数据（正常值/边界值/异常值）每类至少一个场景
- **待源码验证**列标注该场景是否需要源码验证：
  - `否`：场景数据完全来自 AC 语义或业务常识
  - `是：需源码确认边界`：边界值需从源码获取精确数值
  - `是：需源码确认校验规则`：异常值需从源码确认校验规则

### 4. 数据需求清单

**要求**：
- 汇总第 2、3 节的结果
- 每个变量列出三类数据的具体示例值
- 边界值示例如无法从 AC 确定，填"待源码验证"
- 异常值示例基于业务常识填写，标注约束来源

### 5. 分析结论

**要求**：
- 统计数据需准确
- 待源码验证项数量 = 标注为"待源码验证"的变量和场景总数
- 风险提示列出完全依赖源码约束的变量，提示后续重点补充

## Usage Guidelines

生成示例分析文档时：

1. **加载 User Story**：读取 User Story 卡片，提取用户故事和 AC
2. **识别变量**：逐条分析 AC，提取待实例化变量并标注约束来源
3. **定义维度**：为每条 AC 定义正常值/边界值/异常值测试场景，标注待源码验证项
4. **汇总清单**：生成数据需求清单，标注待源码验证项
5. **得出结论**：统计待源码验证项数量，标注风险

**重要**：
- 本阶段不扫描源码仓库
- 每个变量必须标注约束来源（AC 语义 / 业务常识 / 待源码验证）
- 待源码验证项是后续校正的工作线索

## Best Practices

1. **约束来源必标**：每个变量必须标注约束来源，不可遗漏
2. **待源码验证显性化**：将需要源码确认的约束明确列出，便于后续校正
3. **变量全覆盖**：逐条分析 AC 的 Given/When/Then，不遗漏任何变量
4. **三类数据齐全**：每条 AC 的测试维度必须覆盖正常值、边界值、异常值
5. **业务假设合理**：基于业务常识的假设值应真实合理，便于 `asdm-test-spec-ui-generate` 直接使用

### Common Pitfalls to Avoid

- **遗漏约束来源标注**：未标注变量约束来源，导致后续无法定位待验证项
- **混淆约束来源**：将业务常识误标为 AC 语义，或反之
- **待源码验证项不明确**：仅标注"待源码验证"但未说明需验证什么
- **变量遗漏**：未逐条分析 AC 的 Given/When/Then，遗漏部分变量
