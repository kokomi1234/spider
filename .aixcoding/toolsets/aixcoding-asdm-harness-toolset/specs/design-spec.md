# Spec: FT-{id}-{name}-DesignSpec.md

> 本文档定义 `/asdm-harness-design-parse` 产出的 `FT-{id}-{name}-DesignSpec.md` 的标准结构、字段约束与校验规则。`/asdm-harness-design-details` 与 `/asdm-harness-develop` 读取本文件描述的结构时均以此为准。

## 1. 文件定位

| 项 | 说明 |
|:--|:--|
| 生成方 | `/asdm-harness-design-parse` |
| 消费方 | `/asdm-harness-design-details`（补充数据模型/接口设计等章节）、`/asdm-harness-develop`（实现阶段读取，均为只读） |
| 路径 | `.asdm/workspace/asdm-harness/feat/FT-{id}-{name}/FT-{id}-{name}-DesignSpec.md` |
| 生命周期 | 与设计图目录 `design/` 同级共存；设计图有更新时，通过重新执行 design-parse 覆盖重建，不做增量合并 |
| 覆盖范围 | 一个特性（Feature）对应一份 `FT-{id}-{name}-DesignSpec.md`，内部按「场景」分节覆盖多张设计图 |

## 2. 文档结构

```markdown
# Design Spec — FT-{id} {特性名称}

> 来源设计图：{图片文件名列表，逗号分隔}
> 生成时间：{ISO 8601}
> 解析场景数：{N}

## 场景：{场景名称}（来源：{图片文件名}）

### 布局
{区块划分的自然语言描述}

### 字段清单
| 字段 | 必填 | 类型 | 备注 |
|:----|:----|:----|:----|
| {字段名} | 是/否 | {见 3.2 类型枚举} | {示例值需显式标注"（示例值，非业务要求）"} |

### 交互元素
- {控件名称}：{位置}，{样式：主/次/危险等}，{说明}

### 状态提示
- {提示类型：错误/成功/加载等}：{出现位置}

### 参考 AC 映射（仅供参考，非权威）
- {字段/交互} ↔ {AC 编号}

---
（如有多个场景，重复以上「场景」区块）
```

## 3. 字段级约束

### 3.1 必填列取值

只能是 `是` 或 `否`，不允许留空或写其他描述性文字。若设计图中视觉标记不明确（如无法判断是否有必填星号），标注为 `否` 并在备注中说明"图中未见明确必填标记"。

### 3.2 类型列枚举

只能从以下枚举中取值，无法归类时用「其他」并在备注中补充说明，不允许自造新类型：

```text
单行输入 | 多行文本域 | 下拉选择 | 单选 | 复选 | 开关 | 文件上传 | 日期选择 | 只读展示 | 其他
```

### 3.3 备注列中的示例值标注

设计图中出现的具体文案（占位符、示例数据、mock 内容）必须原样记录并**显式标注来源性质**，格式固定为：

```text
示例值："{原文}"（非业务要求）
```

**禁止**将示例值记录为普通备注文字而不加标注——这是防止 develop 阶段误将示例文案当作业务硬编码的关键约束，design-parse 执行时必须严格遵守。

### 3.4 「参考 AC 映射」的权威性声明

本节内容仅为 design-parse 基于字段名称/位置做出的**弱关联提示**，用于帮助 develop 阶段快速定位相关 AC，**不构成业务规则来源**。行为逻辑的唯一权威来源是 PRD 中的验收条件 (DoD) 与 Plan 文档，`FT-{id}-{name}-DesignSpec.md` 任何部分与 DoD 冲突时以 DoD 为准（该冲突处理规则由 `/asdm-harness-develop` 在实现阶段执行，design-parse 不做取舍判断，只如实记录映射建议）。

## 4. 校验规则

`/asdm-harness-design-parse` 在第 4 步「人工确认」写入文件前，以及 `/asdm-harness-develop` 首次读取时，应做以下结构校验：

```text
(A) 文档级检查
- 必须包含一级标题 "# Design Spec — FT-{id} {特性名称}"
- 必须包含「来源设计图」「生成时间」「解析场景数」三项元信息
- 「解析场景数」需与实际「## 场景：」二级标题出现次数一致

(B) 场景级检查（每个「## 场景：」区块）
- 必须包含「布局」「字段清单」「交互元素」「状态提示」「参考 AC 映射」五个三级标题，
  即使某项为空也须保留标题并写"无"，不可整节省略
- 「字段清单」表格必须包含表头 "字段 | 必填 | 类型 | 备注"
- 「字段清单」每行的「必填」列取值必须 ∈ {是, 否}
- 「字段清单」每行的「类型」列取值必须 ∈ 3.2 定义的枚举
- 「备注」列中若包含示例值，必须匹配 3.3 定义的标注格式

(C) 一致性检查
- 「来源设计图」列出的每个文件名，在 design/ 目录中必须实际存在
- 每个「## 场景：」标题括号内标注的来源图片，必须是「来源设计图」中列出的文件之一
```

> ⚠️ 校验失败时，`/asdm-harness-design-parse` 在人工确认环节需将不一致项列出并要求修正后才允许写入；`/asdm-harness-develop` 读取时若发现结构不满足以上规则，视为 `FT-{id}-{name}-DesignSpec.md` 不可用，按「未解析」处理（即触发 develop 中「设计图预处理状态检测」的阻塞提示，引导重新执行 design-parse）。

## 5. 版本与重建

- `FT-{id}-{name}-DesignSpec.md` **不做增量更新**，每次重新执行 `/asdm-harness-design-parse` 视为全量重建，覆盖旧文件
- 设计图有变更（新增/替换）时，需重新执行整个 design-parse 流程，而非手工编辑 `FT-{id}-{name}-DesignSpec.md`
- 「生成时间」字段用于 develop 阶段判断 spec 是否可能滞后于最新设计图（如设计图文件的修改时间晚于 spec 生成时间，develop 可提示用户确认是否需要重新解析，具体提示逻辑见 develop-spec.md）

## 6. 与其他 Spec 的关系

| Spec 文件 | 关系 |
|:---------|:-----|
| `develop-log.json` | 独立文件，develop 任务状态不记录 DesignSpec 相关信息；DesignSpec 是否就绪由 develop 每次运行时实时检测目录，不落状态 |
| `plan-spec.md` | Plan 文档中若某任务标注为 UI 相关，应能与 `FT-{id}-{name}-DesignSpec.md` 中的「场景」对应，但两者不做强绑定校验，允许人工判断 |
| `prd-spec.md` | design-details 补充数据模型/接口设计章节时，若引用了 DesignSpec 的字段/场景，应在 PRD 对应章节标注引用来源（如"字段定义参见 DesignSpec § 场景：XXX"），但不复述字段清单原文 |
