# Plan 文档规范

## 概述

此规范定义开发实施计划（Plan）文档的结构模板，供 `asdm-harness-plan`（Feature 级，基于 PRD 文档拆解）和 `asdm-harness-us-plan`（US 级，基于单条 User Story 卡片拆解）两个 action 参照。两者共用本文档的通用规范（验证步骤格式、任务类型子节、纵向拆分方法论等），US 级特有的结构差异见文末「US 级 Plan 文档结构」一节。

## 文档命名

```text
FT-{id}-{name}-Plan.md
```

存放路径：`.asdm/workspace/asdm-harness/feat/FT-{id}-{name}/`

> US 级 Plan 的命名规则见文末专节，与本节的 Feature 级命名规则并存于同一目录下，互不覆盖。

## 任务结构规范

### 任务编号

格式：`{Phase}.{Task序号}`，如 `1.1`、`2.3`。

> US 级 Plan 无 Phase 层，任务编号简化为单层，见文末专节。

### 任务类型与描述子节

| 任务类型 | 使用子节 | 内容形式 |
| ----------|---------|---------|
| 基础设施部署 | `#### 部署要求` | 属性值表格（角色、版本、端口等） |
| 微服务/模块新建 | `#### 工程属性` | groupId/artifactId/包路径/端口/技术栈表格 |
| 功能实现 | `#### 核心逻辑` | 处理流程文字描述 |
| 校验/验证类 | `#### 校验范围` | 字段→校验规则对照表 |
| 配置变更 | `#### 配置要点` | 变量名/用途/必填表格 |

本节任务类型划分同时适用于 Feature 级与 US 级 Plan。

### 验证步骤规范

| 规范项 | 要求 |
| --------|------|
| 编号格式 | Feature 级：`V{Phase}.{Task}.{序号}`，如 `V1.1.1`；US 级：`V{Task}.{序号}`，如 `V1.1`（详见文末专节） |
| 格式 | checkbox 列表（`- [ ]`），**禁止使用表格** |
| 内容结构 | 操作描述 → 预期结果，换行后缩进 2 空格跟验证命令 |
| 验证命令 | 优先使用可复制的 shell 命令 |
| 数量 | Feature 级每任务建议 4~8 条；US 级每任务建议 3~6 条（任务粒度更小） |
| 覆盖面 | 正常路径、异常路径、边界条件、安全/认证场景 |

## 任务粒度原则

| 原则 | 说明 |
| ------|------|
| 单一职责 | 每个任务只做一件事 |
| 可验证 | 每个任务必须有明确的交付物和可执行的验证命令 |
| 工作量 | Feature 级理想工作量 1~3 天；US 级理想工作量半天~1 天（US 本身已是 1~3 天原子单元，Plan 内任务应更细） |
| 依赖清晰 | Feature 级同 Phase 内任务依赖线性排列；US 级全部任务依赖线性排列 |

## 拆分方法论：纵向拆分（Vertical Slicing）

**必须采用纵向拆分方式组织任务，禁止按技术层次横向分层。** 本原则对 Feature 级与 US 级 Plan 同等适用。

| 对比维度 | 横向拆分（❌ 禁止） | 纵向拆分（✅ 必须） |
| ---------- | ------------------- | ------------------- |
| 拆分维度 | 按技术层（DB → Service → Controller → Client） | 按用户可感知的能力 / 可验证的功能单元 |
| 单个任务产出 | 中间层，用户不可见 | 端到端可验证的功能 |
| 验证时机 | 多任务完成后才能验证 | 每个任务完成即可验证 |

一个纵向切片 = 从用户视角出发的一个完整功能闭环，穿过所有技术层次但限定在一个具体的、可验证的用户能力上。

## 验证步骤常用模式

以下模式对 Feature 级与 US 级 Plan 通用，仅编号格式随所属层级调整。

### 进程/服务类

```text
- [ ] **Vx.y.z** 检查 {进程名} 状态 → 运行中
  `docker ps | grep {name}`
```

### HTTP 接口类

```text
- [ ] **Vx.y.z** GET/POST {path} → HTTP {code} + {字段断言}
  `curl -s {method} {url} | jq '{expr}'`
```

### 数据库/存储类

```text
- [ ] **Vx.y.z** 验证 {table} 存在且结构正确
  `{client} --query "DESCRIBE TABLE {db}.{table}"`
```

### 编译/构建类

```text
- [ ] **Vx.y.z** {构建工具} 编译成功 → BUILD SUCCESS
  `cd {project} && {build_cmd}`
```

### 认证/鉴权类

```text
- [ ] **Vx.y.z** 带 token 请求 → 放行 → HTTP 200
  `curl ... -H "Authorization: Bearer {token}" ...`
- [ ] **Vx.y.z** 不带 token 请求 → 拒绝 → HTTP 401
  `curl ... -o /dev/null -w "%{http_code}" ...`
```

## US 级 Plan 文档结构

当 Plan 基于单条 User Story 卡片（而非整个 PRD）生成时，即 `asdm-harness-us-plan` 的产出，结构在上述通用规范基础上做以下调整。

### 文档命名

```text
FT-{id}-{name}-US-{序号}-{us名字}-Plan.md
```

存放路径：与 Feature 级 Plan 相同目录 `.asdm/workspace/asdm-harness/feat/FT-{id}-{name}/`，两者共存，通过文件名中的 `US-{序号}` 片段区分。develop-log.json 同理命名为 `FT-{id}-{name}-US-{序号}-{us名字}-develop-log.json`。

### 与 Feature 级的结构差异

- **不设 Phase 层**：任务编号从 `{P}.{T}` 简化为单层 `{N}`，验证步骤编号相应简化为 `V{N}.{M}`
- **「项目概述」替换为「User Story 概述」**：直接引用 US 卡片中的用户故事三段式（作为一个…我想要…以便…），不重复 PRD 背景
- **验证步骤追加 AC 追溯**：

  ```text
  - [ ] **V{N}.{M}** {操作描述} → {预期结果}（对应 AC-{X}）
    `{验证命令}`
  ```

- **新增「AC 覆盖对照表」章节**（替代「变更模块总览」）：

  | AC | 描述 | 覆盖任务 | 覆盖验证步骤 |
  | :--: | ------ | :------: | -------------- |
  | AC-1 | {AC 标题} | 任务 1, 2 | V1.1, V1.2, V2.1 |

  生成 Plan 时必须保证每条 AC 至少出现在此表中一次，否则视为拆解不完整（详见 `asdm-harness-us-plan` Step 3.1「AC 覆盖检查」）。

- **无「变更模块总览」**：单条 US 影响范围已足够聚焦，不需要模块级汇总

### US 级 Plan 文档标准结构

```markdown
# <feature-id>-US-{序号} {US 名称} 实施计划

> **🔗 前置依赖**：本文档基于 [<feature-id>-US-{序号}-<story-name>.md](../../../features/<feature-id>-<feature-name>/user_stories/<feature-id>-US-{序号}-<story-name>.md)（User Story 卡片）拆解生成。

> 📋 **开发进度**：[develop-log.json](./FT-{id}-{name}-US-{序号}-{us名字}-develop-log.json)

> 最后更新：{YYYY-MM-DD}
```
