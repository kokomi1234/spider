# AIxCoding Discover — 业务分析与需求澄清

纯业务分析。通过结构化访谈澄清"用户要什么"。
**不涉及技术方案、不拆 Story、不写 AC**。

## 整合

| 原步骤 | 集成方式 |
|--------|----------|
| asdm-harness-askme | 结构化访谈追问，逐维度探索需求 |

## Input

| 输入项 | 来源 | 必填 | 说明 |
|--------|------|:--:|------|
| 需求描述/业务目标 | 用户 | ✅ | 自然语言，可粗略 |
| 项目上下文 | 00 `.aixcoding/contexts/index.md` | 自动 | L1 必读 |
| 架构概览 | init `layer-2/architecture.md` | 按需 | 跨模块判断 |
| 已有代码 | 源码（Controller/Service） | 按需 | 代码优先探索 |

## 硬性门禁 0（HARD GATE）：任何输出前必须先分配 Feature ID

**在展开任何访谈 / 任何写盘 / 任何文档输出之前，第一步必须先为本 Feature 分配并登记 Feature ID。** 这是一道硬性门禁，不满足不允许进入后续流程。

| 项 | 规则 |
|----|------|
| 格式 | 必须严格匹配正则 `^FT-\d{3}$`，如 `FT-001`（机器友好、全局唯一） |
| 禁止 | **严禁**使用 `Feature 2.5`、`Feature-2.5`、`2.5`、`E1`、`F1`、`1.0` 等展示型/语义化编号 |
| 登记 | 读取并写入当前项目的 `overall-plan.md`，编号递增（取当前最大 FT 编号 +1，补足 3 位），**不复用已归档 ID** |
| 唯一性 | 若 `overall-plan.md` 已存在该 ID，必须换用下一个未占用的编号 |
| 落盘 | 所有产物目录名**必须**用该 ID：`.aixcoding/workspace/discovery/<feature-id>/` |
| 传递 | 该 ID 原样贯穿 design / split / specify / plan 全链路 |

> ❗ 反例（**一律禁止**）：目录名写成 `Feature-2.5-admin-edit-disabled-skill`、`Feature 2.5`、`2.5`。
> ✅ 正确示例：目录名 `FT-001`/`FT-002`…，文档内 `Feature ID: FT-001`。

**分配完成后，立即创建目录 `.aixcoding/workspace/discovery/<feature-id>/`，再进入访谈。**

## Workflow

### 0. 无 Feature 指定时的处理

如果用户未指定新特性：
1. 读取 `overall-plan.md` 了解当前项目规划
2. 分析能力缺口，基于代码库现状向用户提出候选特性
3. 每个候选含：所属模块、业务价值、建议优先级
4. 候选确认后，**仍按「硬性门禁 0」分配 `FT-xxx` 编号**再继续

### 1. 代码优先探索（Code-First）

对于每个决策点，**先扫描代码库**再提问：
- 探索现有模式（相似功能、可复用组件）
- 检查现有 API 和数据模型
- 基于证据提供 AI 推荐方案

### 2. 结构化访谈

逐维度追问，每个维度给 AI 推荐：

| 维度 | 追问内容 | 代码探索 |
|------|----------|----------|
| 业务目标 | 要解决什么问题？为什么现在做？ | 查看现有功能覆盖 |
| 用户角色 | 谁会使用？核心 Persona 是谁？ | 查看现有角色/权限体系 |
| 核心场景 | 用户典型操作路径是什么？ | 查看类似功能的流程 |
| 边界条件 | 什么不算？极限情况是什么？ | 查看异常处理模式 |
| 约束依赖 | 有哪些硬限制？依赖哪些系统？ | 查看 pom.xml/配置 |
| 成功指标 | 怎么做才算成功？可衡量的指标？ | 查看现有监控/埋点 |

### 3. 输出业务需求文档

纯业务语言，不含技术术语。

## 输出门禁（写盘前必查 Feature ID）

写盘 `business-requirements.md` / `interview-notes.md` **之前**，逐项自检并当场修正：

- [ ] 目录名是否匹配 `^FT-\d{3}$`？
- [ ] 文档内 `Feature ID` 字段是否与目录名一致且匹配 `FT-xxx`？
- [ ] 是否已写入 `overall-plan.md`？
- [ ] 是否**完全杜绝**了 `Feature 2.5` / `Feature-2.5` / `2.5` 等字样？

任一项不通过 → **不得产出**，先修正为 `FT-xxx`。

## Output

```
.aixcoding/workspace/discovery/<feature-id>/   # <feature-id> 必须为 FT-xxx 形如 FT-001
├── business-requirements.md   # 业务需求文档
│   ├── 业务背景与目标
│   ├── 用户角色分析（Persona）
│   ├── 核心业务场景（用户故事地图）
│   ├── 业务流程（Mermaid 流程图）
│   ├── 业务规则与约束
│   ├── 非功能需求（性能/安全/可用性）
│   └── 成功指标（可衡量 + 量化目标）
└── interview-notes.md         # 访谈记录（追问+决策+假设+待澄清）
```

## Guardrails

- **Feature ID 必须为 `FT-xxx`（如 FT-001），严禁 `Feature 2.5` / 版本号 / 语义化编号**
- 优先探索代码库，基于证据提供推荐
- 每个决策点给出 AI 推荐方案，减少冗余提问
- 纯业务语言，不出现技术术语
- 访谈记录标注假设和待澄清项
- 目录名与 Feature ID 保持一致，且匹配正则 `^FT-\d{3}$`

## 使用

`/aixcoding-discover <业务描述>`
