# 模块化方案评估：模块注册表 / ESM

> 结论先行、理由在后。
> 评估日期：2026-09-16；对应 TODO「技术债 → 评估是否引入模块注册表 / ESM」。
> 评估基于当场实测（不是估数）：脚本清单、源码扫描、单测与冒烟结果都在下面。

---

## 一句话结论

**不引入 ESM，也不新建模块注册表。**

真正的病根不是「用了 `window.X` 全局名」，而是**模块在 IIFE 顶层就把依赖取进闭包**——
脚本顺序一变，依赖就永久退化成兜底实现，而且**不报错**。
把这批点改成「调用时才取 `window.*`」，就达成了「彻底摆脱顺序敏感」这个目标，
且**零部署改动、零新增全局、不碰 190 个单测的加载方式**。

已按此落地（13 个文件、22 处），单测 190 → **194**，三页浏览器冒烟 **ALL PASS**。

---

## 1. 病根：顺序敏感 ≠ 全局变量多

项目是「无框架无构建」的原生 HTML/CSS/JS，每个模块写成 IIFE，靠 `window.X` 互相取用：

```js
(function () {
  'use strict';
  const notify = window.toast || (() => {});   // ← 问题在这一行
  ...
  window.DictSelects = { ... };
})();
```

`const notify = window.toast || (() => {})` 在**加载那一刻**就定了值。于是：

- `toast.js` 排在 `dict-selects.js` 之后 → `window.toast` 还是 `undefined` → `notify` 永久是空函数；
- 页面**不报错**，只是「点了没反应」「提示不出来」。这正是项目踩过的坑。

所以「顺序敏感」= **加载期捕获**，不是「有多少个 `window.` 挂载」。

## 2. 实测现状

| 现存兜底 | `bootstrap.js` 的 `PRESETS` 按页点名报缺失 + HTML 里的顺序注释 | 只覆盖"缺依赖"，不覆盖"顺序错" |

## 3. 三条路线对比

### A. ESM（`<script type="module">` + `import/export`）——**否决**

| 项 | 评估 |
|---|---|
| 能不能解决顺序敏感 | 能，原生模块依赖图自动排序，这是最干净的解法 |
| **致命卡点：测试脚手架** | `tests/harness.js` 用 `new Function` 加载脚本源码。ESM 的 `import/export` 在 `new Function` 里**根本无法执行**，190 个用例的加载方式要整体重写 |
| 部署改动 | 需要 `type="module"` 改造全部页面 + 必须经 http 提供（现在经代理本来就是 http，勉强可行） |
| 代码改动 | 26 处全局挂载全部改成 `export`，所有消费方改成 `import`；三页 HTML 的 script 标签块要重写 |
| 缺少构建链 | 无打包工具，改动全靠手写；一旦将来想加压缩/校验又得引构建 |
| 净收益 | 消除顺序敏感 —— 但这一条用方案 C 花 1/10 代价就拿到了 |

结论：**收益是「顺序敏感」，代价是「重写测试脚手架 + 重写引入方式」**，不划算。

### B. 模块注册表（`AppModules.register/get`）——**不划算**

把 26 处 `window.X = {...}` 换成 `AppModules.register('X', {...})`，消费方改 `AppModules.get('X')`。

- **不解决病根**：`const M = AppModules.get('X')` 若写在顶层，照样是加载期捕获，顺序问题原样存在。注册表只把「隐式全局」变成「显式且有校验的全局」，顺手多 1 个全局（`AppModules`）。
- 收益（依赖显式化、可校验）**已经被 `bootstrap.js` 的 `PRESETS` 拿到了**，再叠一层是重复建设。
- 要动 26 个挂载点 + 全部消费方，风险与工作量都远大于方案 C。

### C. 惰性取值（调用时才取 `window.*`）——**采用**

把「加载期捕获」改成「调用期解析」。项目里其实早就有这个约定，只是没铺开：

- `js/ui/table-utils.js` 文件头就写着：*「esc 延迟到调用时再取 window.Fmt，不放在 IIFE 顶部」*；
- `js/page/publish-query.js` 用 `const M = () => window.PublishModel;`；
- `js/core/api-client.js` 也注明「传输层延迟取 window.API.call」。

统一成两种写法：

```js
// ① 纯函数别名：包一层箭头，函数体里再取
const notify = (...a) => (window.toast || (() => {}))(...a);
const esc    = (v)     => ((window.Fmt && window.Fmt.esc) || ((x) => String(x ?? '')))(v);

// ② 命名空间 / 对象：改成取值函数，用到的 3~5 行跟着加 ()
const QF = () => window.QueryFeedback || { setLoading() {} };
function showLoading() { QF().setLoading(true); }
```

**代价**：0 个新全局、0 处部署改动、单测加载方式不变。
**收益**：脚本顺序怎么排都不影响（有回归用例钉住）；顺带修掉一个**真实潜在 bug**（见 §4）。

| `js/data/batch-data.js`、`department-data.js`、`provider-data.js` | `debugLog` 改惰性 |

**有意保留**的加载期捕获（属「有声失败」，不算病）：

- `js/page/index.js` 的 `PublishModel` / `PublishView` / `PublishQuery` / `FIELDS`；
- `js/page/subscription.js` 的 `SubscriptionModel.*` / `SubscriptionView` 系列。

理由：它们下面**紧接着就解引用成员**（`PublishModel.FIELDS`、`SubscriptionModel.rowKey`），
错序会**当场抛 `TypeError`**——用户与控制台立刻看得见，配合 `bootstrap.js` 的 PRESETS 点名，
不会变成"静默失效"。硬要改就得引入懒代理或改掉 30+ 处调用点，成本大于收益。
（`js/page/index.js` 里已写了注释说明这一点。）

`js/core/bootstrap.js` 的文件头注释同步更新（原文「模块加载时就把 window.X 取进闭包」已不再成立）。

## 5. 回归防线：`tests/module-order.test.js`

两层，都是新加的：

1. **运行时**（3 条）：故意把被依赖模块排到后面加载，断言依赖仍生效——
   - `task-api.js` 先于 `api-client.js` 加载 → `fetchTaskList` 仍返回 `ok:true`（旧代码会返回「请求层未就绪」）；
   - `service-api.js` 先于 `api-client.js` → `subscribeWithForm` 仍真的发出请求；
   - `tool-api.js` / `user-api.js` 同上。
2. **静态**（1 条）：扫描 `js/` 全部源码，IIFE 顶层不得再出现「会静默降级」的捕获。
   带**反向断言**——白名单里的条目必须仍能被扫到，否则报「扫描逻辑失效 / 白名单过期」，
   防止这条防线哪天变成「假装在防」。

## 6. 什么情况下才该回头上 ESM

满足任意两条再考虑：

- 真的引入了构建链（rollup / esbuild / vite 任一），`import` 能被编译成现有形式；
- 页面数量或模块数量明显再涨（比如 > 40 个模块），手写 `<script>` 顺序开始成为负担；
- 需要按需加载 / 代码分割（当前三页各自全量加载，用不上）；
- `tests/harness.js` 有了 ESM 版加载器（否则 190+ 用例要整体重写）。

在那之前，「调用时才取 + `bootstrap.js` 点名 + 顺序回归用例」这三件套已经足够。
