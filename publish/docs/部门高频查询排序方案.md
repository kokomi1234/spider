# 部门「高频查询」排序改进方案

> 面向：`publish/lib/queries-db.js` 的 `deptTop()`（服务端排行）+ `js/ui/saved-query.js` 的部门查询。
> 写于 2026-09-21，只做设计，未改代码。文内"实测"均指本机离线代理（3014）上的真实数据/真实点击。

---

## 0. 结论先给

**推荐：指数时间衰减的「按人贡献求和」分数（半衰期 30 天）。**

```
某条查询在某部门的分数 = Σ（该部门每个人） 2 ^ ( −(现在 − 这个人最后活跃时间) / 半衰期 )
```

- 排序按这个分数降序；**不需要定时任务**，读取时算即可（条目数很小）。
- 半衰期 **30 天**、展示 **10 条**（备 20 条）、部门内参与计算的上限 **50 条**。
- **前置条件**：必须先修「使用上报」链路（见 §3.2）—— 否则衰减没有数据可用，方案退化成现在这样只能靠保存人数。

选它的核心理由（对应你的约束）：**它是唯一"单调连续"的方案——不产生窗口边界，所以榜单不会突然重整**，这正好是你要的"稳定、不抖动"。

## 1. 现状：两个和直觉不一样的事实（先校正前提）

### 1.1 现在根本不是按"查询次数"排的

`deptTop()` 的 SQL 结尾是：

```sql
ORDER BY agg.savers DESC, agg.last_saved DESC
```

即 **按「本部门里保存过这份条件的人数」降序**，人数相同时才比最近保存时间。`hits`（打开次数）字段存在，**但没参与排序**。

所以你说的"很久以前的查询长期占据高频位置"这个痛点是成立的，但成因是：
**`savers` 是单调累加的人数——保存过就永久计入，没人用也永远算 1 人**。它只增不减，自然会沉淀。

### 1.2 `hits` 不可信，而且现在连"最近打开时间"都写不进去

| 环节 | 现状 | 影响 |
|---|---|---|
| 服务端合并语义 | `hits=MAX(库里的, 这次推的)` | 是"**单台机器上的最大次数**"，不是全部门累加。张三在自己机器上开 10 次、李四开 3 次 → 库里是 10，不是 13 |
| 前端上报时机 | 点首页卡片 → `hit()` → 写本机 + `fetch` 推服务端 → **同一时刻 `<a>` 开始跳转** | 导航会中断在途 fetch，上报经常丢失 |
| 落地覆盖 | `syncFromServer()` 用服务端返回的「我的列表」**覆盖**本机镜像 | 本机 +1 的那次，下次同步被服务端旧值盖掉，计数没了 |

**实测**（点一次首页卡片，前后读库）：

```
点之前: hits=1  lastAt=2026-09-20T16:00:29Z
点之后: hits=1  lastAt=2026-09-20T16:00:29Z     ← 完全没变
```

也就是说：**"打开"这件事目前既没记到次数，也没记到时间**。这解释了为什么库里三条记录的 `lastAt` 全是 0、排序只能靠 `savers`。

> 这条对方案是决定性的：任何依赖"次数"的做法，都得先修上报；而只依赖"保存"也能做衰减（用 `saved_at`），代价是"用过但没保存"的活跃度体现不出来。

## 2. 四种做法的对比

| 方案 | 思路 | 优点 | 缺点 | 实现复杂度 | **抖动（你最在意的）** | 适用场景 |
|---|---|---|---|---|---|---|
| **① 指数时间衰减**（推荐） | 分数随时间连续衰减，使用则加分 | 连续单调、**没有边界所以不抖**；不用存历史明细；读写都是 O(条目数) | 要存"最后活跃时间"；参数是半衰期，需要挑 | **低** | **极低** | 条目少、要求稳 ✅ 本场景 |
| ② 滑动时间窗口 | 只统计最近 N 天的次数 | 语义最直观（"近 30 天用了几次"） | 满 N 天的访问**整批掉出窗口** → 计数阶跃 → 榜单突变；要存明细或按天分桶 | 中～高 | **高**（窗口边界效应） | 数据量大、且明确要"最近 N 天"口径 |
| ③ 固定 TTL / 过期 | 超过 N 天没用就淘汰或降权 | 最简单，一眼看懂 | **悬崖式**：到期的瞬间从榜单消失；不表达"半热" | 极低 | 中（突变发生在到期点） | 纯缓存淘汰，不适合榜单 |
| ④ 冷热分层 | 热数据实时算、冷数据归档 | 大数据量下性能好 | 层间迁移本身也会造成跳动；对这个体量是杀鸡用牛刀 | 高 | 中 | 百万级条目 |

### 为什么明确不选 ②（滑动窗口）

它最符合"近期热度"的直觉，但恰好违背你的硬约束：

- 某条查询在第 31 天，第 1 天的 5 次访问**同时**掉出 30 天窗口 → 计数从 12 掉到 7 → 可能一步跌出前 10。
- 这种阶跃是**周期性的、可感知的**：榜单会在某些天"大洗牌"，用户会以为是 bug。
- 指数衰减没有这个问题：老访问的权重是**逐日平滑减少**的，第 31 天相对第 30 天只差 `2^(-1/30)` ≈ 2.3% 的因子。

### 为什么不选 ③ / ④

- TTL 的"悬崖"同样是抖动，只是频率低；而且它无法表达"半热"（用过但不多）。
- 冷热分层是为性能设计的，本场景部门内条目是个位数到几十条（实测当前只有 3 个聚合组），没有任何性能压力，引入分层只会增加状态和 bug 面。

## 3. 推荐方案的设计

### 3.1 分数公式

对某条查询（按 `fingerprint` 聚合，口径与现状一致）在某个部门内：

```
score(dept, query) = Σ over 本部门保存过它的人 p:
                        w_p × 2 ^ ( −(now − lastActive(p, query)) / H )

  lastActive(p, query) = MAX( p.saved_at , p.last_used_at )
  w_p                  = 1（人人都一样；预留给以后加权限/角色权重）
  H                    = 半衰期（毫秒）
```

含义很好讲给业务听：**"一个人 30 天前用过这份查询，对今天的排序只算半个人；90 天前用过，只算 1/8 个人。"**

几个直接推论：
- 部门里**多人在用** → 分数叠加，仍保留现在"人数多更靠前"的语义 ✅（不是推翻，是加时间维度）
- 某人**长期不用** → 他那份贡献趋近 0 → 这条自然下沉 ✅（就是你要的自动降权）
- 某人**今天用了** → 他那份回到 1 → 立刻上浮 ✅

### 3.2 数据字段

| 字段 | 位置 | 现状 | 改动 |
|---|---|---|---|
| `saved_query_savers.saved_at` | 已有 | 可靠（INSERT 时写入） | 不动 |
| `saved_query_savers.last_used_at` | **新增一列** | 无 | **新增**，记录"这个人在本部门内最后一次使用这份查询" |
| `saved_queries.last_opened_at` | 已有 | 有字段、但上报丢失（§1.2） | 保留，作为**兜底**（分人记录缺失时用它的 MAX） |
| `hits` | 已有 | 不可信（MAX 合并） | **不参与排序**；可留作诊断 |

按人存（而不是只存一条全局时间）是这套方案的关键：否则"张三天天用、李四半年没用"和"两人都半年没用"会算成一样。

### 3.3 更新时机（关键：不要在跳转前上报）

现在丢数据的根因是"点了卡片 → 上报 → 同一刻跳转"。改成**落地页上报**：

```
首页点卡片（只跳转，不再上报）
      ↓  URL 带着 ?saved=<id>
落地页（publish / task / subscription）加载完成
      ↓  认出 ?saved=，上报一次「我用了这条」
服务端：UPDATE saved_query_savers SET last_used_at = now
        WHERE query_id = ? AND user_key = <当前用户>
```

好处：
1. **不受导航中断影响**（跳转已经完成，页面没在卸载）。
2. **语义更准**：记的是"真的打开并加载了"，而不是"手滑点了一下"。
3. 落地页本来就有 `?saved=` 的回填逻辑（`publish.js` 的 `restoreSavedQuery`），加一步上报是顺路的。

> 备选（若不想动落地页）：在 `hit()` 里改用 `navigator.sendBeacon`（`pushToServer` 已有 beacon 路径，浏览器保证卸载时送达）。但 sendBeacon 拿不到响应、也不知道成功没有，落地页方案更可控。

**定时重算：不需要。** 衰减是时间的纯函数，读取时算即可；条目数个位数到几十条，一次遍历完全可以接受。唯一建议的定时任务是**清理**（见 3.5）。

### 3.4 关键参数建议

| 参数 | 建议值 | 理由 |
|---|---|---|
| 半衰期 H | **30 天** | 与业务节奏一致：批次是月度的（2607~2612），30 天 ≈ 一个批次周期。30 天前用过的≈半票，90 天前≈1/8 票，正好让"上季度的习惯"让位给"这个月的" |
| 候选/展示条数 | 取 **20**、展示 **10** | 你说 10~20 条；多取一倍是为了让"即将上来"的条目先在候选里，避免展示层抖动 |
| 参与计算的部门上限 | **50 条/部门** | 现状 `byUser` 的 limit 就是 50，口径对齐；超出只取最近活跃的 50 条 |
| 事件权重 | 保存 = 1.0，使用 = 1.0 | 都是"这个人关心这份查询"的信号。若以后想让"用"比"存"更值钱，把 `last_used_at` 的权重调到 1.2 即可，不用改结构 |
| 淘汰阈值 | 分数 < **0.05** 且 180 天无活动 | 0.05 ≈ 半衰期的 4.3 倍时间（约 130 天）无人问津；180 天是双保险，避免边界反复 |

**半衰期怎么挑**：如果上线后觉得"换得太快"，把 H 调到 45~60 天；如果觉得"老面孔还是下不去"，调到 14~21 天。**只改这一个常量**，不动结构。

### 3.5 冷启动

- 新查询被第 1 个人使用 → 分数 1.0。
- 一条 3 人保存但 90 天没人用的老查询：3 × 2^(-3) = **0.375** < 1.0 → **新人新查询立刻排在它前面** ✅ 这正是你要的"近期真实需求浮上来"。
- 一条 3 人保存且**每天都在用**的老查询：分数 ≈ 3.0 → 仍稳居第一 ✅ 这没问题，它本来就该在前面。

**所以不需要给新查询额外的"冷启动加成"**：加成反而会让榜单在"新查询出现"和"新查询过期"两个时点各抖一次。用的人多了自然上去，这是自洽的。

如果确实想给新东西一点曝光，建议在**展示层**做（例如榜单下方单独一块"最近新增"），而不是污染排序分数——这样主榜单的稳定性不受影响。

## 4. 对现有排序的影响与验证

### 4.1 影响（用库里的真实数据推演）

当前库里（K4229 部门）按 fingerprint 聚合后只有 3 组：

| 查询 | savers | 现状排名 |
|---|---|---|
| 27年6月独立 E00301-… | 4 | 1 |
| 调用方系统：E00404 | 3 | 2 |
| 调用方系统：E00406 | 2 | 3 |

- **只改排序、数据不变**时（因为 `lastAt` 现在全是 0，`last_saved` 也没有分人记录）：三组分数会一起按同一个衰减因子缩，**相对顺序暂时不变** —— 也就是说上线第一天榜单看起来"没变化"。这是好事（平滑过渡），但也说明**必须先把使用上报修好，衰减才真正开始起作用**。
- 上报修好后，随着 `last_used_at` 积累，预计 2~4 周内榜单开始与"现状"分化：常用的人少的会上移、不常用的人多的会下滑。

### 4.2 怎么验证效果（4 条，都由低到高）

1. **离线回放（上线前就能做）**
   把库里现有条目导出来，分别按"现状 savers"和"新分数"排序，输出两份 Top10 做 diff。
   再叠加"时间旅行"：模拟 30 / 60 / 90 天后（期间无人使用）的排序，确认老条目是**平滑**下滑而不是突然消失。
   > 脚本已跑过一版（`/tmp/sim-dept-rank.js`），当前数据因为 `lastAt` 全 0 看不出差异 —— 这本身就是 §1.2 的证据。

2. **上报链路验证（必须先过）**
   就是 §1.2 那个测试：点一次卡片，前后读库的 `last_used_at` / `hits`，**必须看到变化**。现在这一条是**失败**的，修完才能继续。

3. **抖动量化**
   模拟 30 天、每天 1 人使用同一条，统计榜单 Top10 的**顺序变化次数 / 进出榜次数**，与滑动窗口方案对比。预期：指数衰减远低于滑动窗口（衰减是连续单调的，没有阶跃）。
   判据建议：**稳定期（无新事件）内榜单完全不变；有少量新事件时，一个月内的进出榜次数 ≤ 3**。

4. **真机灰度**
   先只改排序显示、不改数据（双写新旧两种分数，页面上先按旧的分），观察两周让业务侧确认"排序变化是合理的"；再切到新分数。
   同时保留一个诊断输出（每条的分数、最后活跃人、最后活跃时间），便于业务质疑时当场解释"它为什么排第一"。

## 5. 建议的实施顺序

1. **修上报**（前置，必须）：落地页 `?saved=` 上报 + `saved_query_savers.last_used_at` 建列。用 §4.2-2 验证。
2. **双写分数**：`deptTop()` 同时返回旧排名和新分数，先不改展示。用 §4.2-1 回放diff。
3. **切排序 + 加诊断**：按新分数排序，保留"最后活跃人/时间"可见（便于解释）。
4. **加清理**：分数低于阈值的条目不再返回（先不物理删除，保留可恢复）。

## 6. 实现成本：麻烦的到底是哪一步

> 2026-09-21 补：有人问"这样算起来不会很麻烦吗"——把成本拆开量一遍。

### 6.1 计算量：可以完全不考虑

本机基准（`/tmp/bench-decay.js`，Node 22）：

| 场景 | 耗时 |
|---|---|
| 按人求和，现状规模（3 条 ≈ 9 次 `pow`） | **0.1 µs** |
| 按人求和，未来规模（50 条 × 4 人 = 200 次 `pow`） | **0.9 µs** |
| 现状 `deptTop` 一次接口往返（含 SQLite 聚合） | **17 ms** |

**一次全量重算 ≈ 1 微秒，是接口往返的 1/19000。** 不需要缓存、不需要增量维护、不需要为它做任何优化。

### 6.2 真正的改动只有三处

**① 加一列**：`saved_query_savers.last_used_at`（记录"这个人最后一次用这份查询"）。

**② `deptTop()` 的 SQL 加一行聚合、改一处 ORDER BY**（现在这段在 `lib/queries-db.js` 的 295 行附近）：

```diff
   agg AS (
     SELECT gid,
            COUNT(DISTINCT user_key) AS savers,
            MAX(saved_at) AS last_saved,
            GROUP_CONCAT(user_name, '"|;"') AS people,
+           -- ⚠️ SQLite 的 `/` 是**整数除法**，必须先把分子转 REAL，否则指数被截断成整数：
+           --    实测（SQLite 3.51.2）15 天前活跃的情况：
+           --      不转：POW(2.0, -(15天)/30天) → 指数被整除成 0 → 结果 1.0（衰减完全失效！）
+           --      转了：0.7071067811865476 ✅（= 2^(-0.5)）
+           SUM(POW(2.0, -(? - MAX(saved_at, last_used_at)) * 1.0 / ?)) AS score   -- 半衰期衰减
     FROM scoped
     GROUP BY gid
   )
   ...
-  ORDER BY agg.savers DESC, agg.last_saved DESC
+  ORDER BY agg.score DESC
```

（`scoped` 里顺带把 `s.last_used_at` 选出来即可；两个 `?` 是 `now` 和半衰期毫秒数。
SQLite 有 `POW`；想在 JS 里算也行，候选只有几十条，更好调试。）

**③ 上报时机改到落地页**——这是**唯一真正要写点代码**的一步，原因见 §1.2：
现在点卡片时 `fetch` 会被 `<a>` 的跳转中断，实测点了 `hits` / `lastAt` 都不变。

### 6.3 想再省，就分两步走

- **第 1 步**：只修上报（落地页 `?saved=` 时 `UPDATE ... SET last_used_at = now`），
  排序**先不动**。这样先把数据攒起来，零风险。
- **第 2 步**：等 `last_used_at` 攒了两周数据，再加 `score` 聚合、切 ORDER BY。

### 6.4 不建议的省法

**"不按人记，整条记一个 `last_used_at`"** —— 省不掉多少（同样要加一列、同样要修上报），
但会**高估**：一个人天天用，整条会按"全部保存人数"上浮（4 人保存、只有 1 人在用 → 按 4 票算）。
按人版**天然去重**（每人最多贡献 1 票），还顺手解决了"单人反复打开刷分"的问题，性价比更高。

### 6.5 一句话总结成本

**加一列、改一行 SQL、把上报从"跳转前"挪到"落地后"。** 没有定时任务、没有明细表、没有分桶、
没有缓存——与"查询量不大"的体量完全匹配。完全匹配。
