# 订阅报文预演台（DRY RUN）使用说明

> 模块：`publish/js/ui/subscribe-dryrun.js` → `window.SubscribeDryRun`
> 目的：在**不产生任何真实写入**的前提下，看清「点确认订阅」到底会发出什么报文、哪些字段为空、必填与格式校验会不会放行，从而离线对照抓包逐字段核对。
> 入口页：`index.html`（也已登记进 `bootstrap.js` 的 index PRESETS 与冒烟全局清单）。

## 一、为什么可信：走真代码 + 双层拦截

| 环节 | 用的是不是线上那份实现 |
| --- | --- |
| 必填/格式校验 | ✅ `SubscribeModel.validateSubscribe` / `validateJudgeSubmit`（原函数、原入参口径） |
| 订阅报文组包与发送 | ✅ `ServiceApi.subscribeWithForm` → `buildSubscribeBody` |
| 评委报文组包与发送 | ✅ `ToolApi.submitSubscriptionReview` → `toJudgeInfoList` |
| 传输层 | ⛔ 被替换：`window.API.call`（第 1 层）+ `window.fetch`（第 2 层）都被换成桩，捕获请求后回放假 200 |

- 全项目请求都经 `api-client` 的 `fetch`（无 XHR），所以两层都拦住 = 不可能发出真实请求；`run()` 返回的 `fetchCalls` 与冒烟里的「网络层泄漏计数」会直接暴露任何漏网。
- 跑完**必然还原** `window.API.call`（否则页面后续请求会被吞），`restored` 字段可查。

## 二、用法 A：点击驱动（推荐 —— 用真实点击走完整交互链路）

```text
1) 打开页面时带上参数：  index.html?dryrun=1      ← 加载即进入预演模式
   （或控制台执行一次：    SubscribeDryRun.enable() ）
2) 照常操作页面：点结果行的「订阅」→ 弹窗里填好 → 点「确 认」
3) 控制台自动打印两个被拦截的写请求（setSubcription / subscriptionReview）与字段明细
4) 结束：点右下角浮标，或 SubscribeDryRun.disable()
```

- **写请求被拦下且不写入后端**；**读接口一律放行**（照常发真实请求），所以查询、下拉、批次加载等行为与平时完全一致。
- 弹窗会像真订阅成功那样：走完校验 → 本地标记「已订阅」→ 提示成功 → 自动关闭；所以整条交互链路与失败链路都能真实观察到。
- 浮标 `🧪 订阅预演中 · 已拦 N 条写请求 · 点此关闭` 一直显示，避免忘记自己处于预演模式。
- 被**校验拦下**（不发请求）时，控制台以 `💬 页面提示：…` 镜像弹窗提示 —— 这是「该拦有没有拦住」的证据。

模拟失败链路（观察「订阅失败」或「评委失败 → 只补交评委」）：

```js
SubscribeDryRun.enable({ fail: 'subscribe' })   // 订阅写入返回 500
SubscribeDryRun.enable({ fail: 'review' })      // 订阅成功、评委写入返回 500
```

**副作用与撤销**：预演成功会把该服务标记为「已订阅」写进 localStorage（模拟成功的必要部分）；`disable()` 会把它撤销（`offReverted` 里能看到撤了哪些编码）。

## 三、用法 B：脚本驱动（辅助 —— 不想点、或想批量看）

```js
// ① 用当前订阅弹窗里的真实表单预演（先打开弹窗、填好表单再跑）
SubscribeDryRun.run()

// ② 校验不过时也想看报文（仅观察，真实提交仍会被前端拦下）
SubscribeDryRun.run({ force: true })

// ③ 显式注入数据（不依赖弹窗）
SubscribeDryRun.run({ row, form, judges, defaultsFetched: false, isSubscribed: () => false })

// ④ 只打印一份报文
SubscribeDryRun.dump(body, '标签')

// ⑤ 跑完整场景矩阵（30 项，逐条给「期望 / 实际」）
SubscribeDryRun.scenarios()
```

弹窗没打开时 `run()` 会回落到**内置示例**并在输出里标明来源，因此离线也能看到完整报文。

两种用法的分工：**点击驱动**回答「我这一版表单点下去会发什么、会不会被拦」；**场景矩阵**回答「所有必填/格式分支是否都符合预期」（它把 30 种输入各跑一遍，逐条打印期望与实际）。

## 四、覆盖场景（30 项，`scenarios()` 逐条输出期望与实际）

### 1. 必填缺失（11 项）
| 场景 | 期望 |
| --- | --- |
| 必填齐全 | 通过 |
| 无行数据 | `no-row`（静默，无文案） |
| 行缺服务编码 | `no-coding` |
| 已在订阅列表 | `subscribed` |
| 未选调用方系统 | `no-caller` + 聚焦 `sub_callerSystem` |
| 未选关联文档 | `no-doc` + 聚焦 `sub_relDoc` |
| 服务编号空且推不出（无 TO 尾号） | `no-service-no` + 聚焦 `sub_callerServiceNo` |
| 服务编号空但可派生（调用方系统 + TO 尾号） | 通过（防「后端拼得出来、前端却拦」的假失败） |
| 评委为空且未拉取默认评委 | `no-judges` + 聚焦 `btnFetchJudges` |
| 评委为空但已成功拉取默认评委 | 通过（唯一豁免） |
| 任务编号为空 / 纯空白 | `no-task-no` + 聚焦 `sub_taskNo` |

### 2. 字段为空 / 参数格式错误（8 项）
| 场景 | 期望 |
| --- | --- |
| TPS 为空 | `no-tps` |
| TPS `abc` / `5a` / `-1` / `0` / `5.5.5` | `bad-tps`（5 条，逐条列示） |
| TPS 全角 `５` | 通过（先归一再看数值） |
| 批次为空 | 通过 —— **刻意不硬拦**：该下拉当前不进报文（`prodBatch/prodBatchList` 只取 row） |

### 3. 校验顺序（2 项）
- 编码缺失 + 系统未选 → 先报 `no-coding`（不是 `no-caller`）
- 评委缺失 + 任务编号缺失 → 先报 `no-judges`（评委区在任务编号之前）

### 4. 组包与发送（9 项）
| 场景 | 期望 |
| --- | --- |
| 完整输入 | 捕获 2 个请求且顺序 = `setSubcription` → `subscriptionReview`，`fetchCalls=0` |
| 评委报文 | 每条 7 键，`judgeRoleId` 按抓包映射（调用方=03 / 服务方=05），`judgeDeptId` 透传 |
| 字段为空：行无 `serverNo/taskNo` | `serverNo` / `prodTaskNo` 用表单任务编号兜底 |
| 行有 `serverNo` | 以行为准，表单值不顶掉 |
| TPS 取值优先级 | 行 `prodTPSPeak` 优先；行里没有才用表单 |
| 无评委行 | 只发订阅报文（与线上一致） |
| 校验不过 | 直接拦下、**不构造报文**（`skipped` 有值） |
| `force: true` | 校验不过也把整条链路构造出来（仅观察） |

## 五、规则来源（每条规则的出处）

| 规则 | 来源 |
| --- | --- |
| 必填顺序：行 → 编码 → 已订阅 → 调用方系统 → 关联文档 → 服务编号 → TPS → 评委 → 任务编号 | `js/ui/subscribe-model.js` 的 `validateSubscribe` 实现顺序 |
| TPS 必须是 > 0 的数字、全角先归一 | 同文件 `normalizeDigits` + 正则 `/^\d+(\.\d+)?$/` |
| 服务编号派生（调用方系统 + 行编码尾号 `TOxxxx`） | `deriveCallerServiceNo`，与 `service-api.js` 的 `providerSysServeNo` 同源 |
| 评委必填、唯一豁免是「已成功拉取默认评委」 | `validateSubscribe` 的 `judgeState.defaultsFetched` 分支 |
| 批次不硬拦 | `service-api.js`：`prodBatch/prodBatchList` 只取 row，表单批次未进报文 |
| 报文 117 个字段、字段顺序、协议常量 `isChecked='1'` / `isDelete='1'` / `reviewStatus='03'` | `service-api.js` 的 `buildSubscribeBody` + `analysis/har/订阅.json` 的真实 `setSubcription` |
| 评委报文 7 键与 `judgeRoleId` 映射（03/05）、`judgeDeptId` 口径 | `subscribe-model.js` 的 `judgeFieldsFromApi` / `JUDGE_ROLE_IDS` / `toJudgeInfoList` + `analysis/har/订阅.json` 两次 `subscriptionReview` |
| 发送顺序：先订阅、评委失败只补交 | `subscribe-dialog.js` 的 `confirmSubscribe`（与抓包请求 0 → 请求 1 的顺序一致） |

## 六、控制台输出的结构与字段顺序

```
【开启横幅】预演模式已开启 + 拦截范围（取自各接口模块的 endpoints）+ 关闭方式
【头部】输入来源（当前弹窗 / 显式传入 / 内置示例）、时间、行数据、表单摘要
【校验顺序】一行说明规则的先后
【一】validateSubscribe 结果   → 通过 / ⛔ 拦下 + code + 文案 + 焦点 + duration
【二】validateJudgeSubmit 结果 → 无评委行时说明「与线上一致：不提交评委」
【请求 n/N】METHOD 路径                     ← 点击驱动时，每个写请求一段这样的打印
    顶层键（报文键序）：documents、publishSubcription
    ── <对象段>：N 个字段 → 非空 X / 空 Y（按报文键序）
        序号  字段名                        取值                      ← 来源标注
    ── <对象段> 的空值字段（Y 个，未发送有效值；每行 8 个）
    ── <数组段>：N 条
        [1] key=value  key=value(空)  …
    ── 完整报文（可整体复制；字段顺序与 JSON 一致）
   💬 页面提示：…                              ← 镜像弹窗提示（被拦下时只有这里有证据）
【三】发送顺序（与抓包一致）
【本次点击小计】共拦截 N 个写请求 + 每个报文的非空统计
【四】安全检查：API 层拦截次数、fetch 层调用次数、传输层是否已还原
【关闭摘要】共拦截 N 个写请求；撤销了哪些本地「已订阅」标记
```

点击驱动的拦截横幅长这样（`N` 是累计序号，同一次「确认」的两个报文会标明「与上一个请求属同一次确认」）：

```
🧪 订阅预演（DRY RUN）· 第 1 个写请求已拦截 —— 未写入后端
触发：前端点击　时间：2026/9/18 12:55:19
```

口径与顺序规则：

- **字段顺序** = `Object.keys(body)` 的顺序 = `buildSubscribeBody` 的构造顺序 = `JSON.stringify` 的顺序。因此打印出的序号可以直接与抓包报文逐行对照，不做任何重排。
- **空值判定**：`null` / `undefined` / 只含空白的字符串 / 空数组算「空」；数字 `0` 与布尔 `false` 算**非空**（是有效取值，不与空串混为一谈）。空值字段不逐条打印取值，只列字段名（避免 88 行噪音）。
- **取值格式**：字符串带引号（能看出首尾空格）、对象/数组转 JSON、超过 46 字符截断并加 `…`。
- **来源标注**：仅对 **关键字段**（37 个，见模块里的 `FIELD_SOURCES`）标注来源（`row.x` / `form.x` / 派生 / 协议常量），其余字段留空 —— 不做没有依据的猜测。

## 七、边界与局限（务必知道）

1. 预演**只验证前端**：前端校验通过 ≠ 后端一定接受。协议常量、字段取值是否被后端认可，仍需一次真实提交或后端确认。
2. **只有写请求被拦**：读接口照常发真实请求 —— 所以离线/内网不通时，页面照样会报「批次加载失败」之类的错误，那是环境问题，与预演无关。
3. 预演**不会**写后端，但会改**本地**订阅状态（模拟成功的必要部分）；`disable()` 会撤销预演期间新增的标记。若你在开启期间手工改过订阅清单，撤销范围以「开启时的快照」为准。
4. 浮标存在期间（预演模式开启中）别做真实订阅操作 —— 那也会被拦成「模拟成功」，只标记到本地。
5. 弹窗已关闭时 `run()` 走内置示例（输出里会写明「内置示例」），不要把它当成当前表单的结论。
6. 评委报文只在「有评委行」时构造；评委为空且走豁免（已拉取默认评委）时不会有第二个请求 —— 与线上一致。

## 八、回归保护

- 单测：`tests/subscribe-dryrun.test.js`
  - 口径层：空值判定 / 取值格式化 / 报文结构描述（字段顺序 = 报文键序）
  - 预演语义：走真实组包函数、真实 fetch 调用次数必须为 0、传输层必须还原
  - 点击模式：写请求被拦且不穿透真实 `API.call`、**读接口放行**（含名字里带 `subscribe` 的读接口这个坑）、
    `disable` 还原 + 撤销本地标记、`enable({fail})` 的失败形状、重复开关幂等
  - 场景矩阵：30 项全部符合预期
- 冒烟：`tests/smoke-browser.js` 两段
  - 「订阅预演台自检」：真实浏览器里跑完 30 场景 + 网络层确认零真实请求
  - 「点击驱动预演」：`?dryrun=1` 自动开启 → 填表 → **点「确 认」** → 两个报文被拦、浮标计数、
    弹窗关闭、本地标记；`disable()` 撤销标记并还原传输层；网络层确认零真实写请求
